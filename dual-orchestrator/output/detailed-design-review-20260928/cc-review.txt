2. 三个重点问题

分期批准是否兼顾严格授权与有界推进——成立。 授权侧三道人门保留且有增强：GOAL 批准（目标/验收/禁区）、contract_review 后移至复评后批精确范围+权限（“approve 才给精确写权限”）、最终候选批准；EXECUTION 资格永久排除 GOAL 冒充（§2.1）；“缺配置默认为已授权”被禁止。推进侧：design/plan READY 不再强制等待，且 §2.3 失效矩阵划清了“程序可续”（目标/范围/权限/必需验收四维核验通过）与“必须新批准”（任一超界）的界——这正是 R3 产品要求 1 的精确化。关键护栏在位：“不把 reviewer READY 记录为 human_action=approved”、“移门不删 reviewer”、AuthoredExecutionContext 区分 reviewed candidate 与 execution authorization。预算沿 definition max_revisions，不静默增加。

本地恢复与外部未知是否分清——分清了，且三机制咬合。 D06 prepared manifest “只负责完成同一次提交”，恢复不重算路由、不再批准、不触碰 provider/Git；D07 的 dispatch intent 在触碰外部进程之前耐久落盘，intent 后无可信完成即进入不明窗口、禁止自动再调用，--prompt-retries 不得绕开；D09 的 apply_intent/observation 让 Git 窗口的“已知/不明”由事实派生而非 status 推测。反向也成立：“本地完成零新 provider”、“不能重新调用 provider 来补本地写”。两层身份（frozen composition / per-occurrence）与“合同修订是新 occurrence 不是 binary 变化”的区分与 R3 一致。

§13 是否准确、有无关键问题后移——基本准确，一处遗漏（见 WARN-1）。 逐项检查十个“仍需完成”：除 D02 的 contained-permission 关联（有保守默认“缺证据不容纳”）外，均为枚举/盘点/可行性核验类工作，不是伪装的设计决定；D04 被诚实标为最硬阻塞并给出向用户提交选项的退出路径。WARN-1 是唯一未登记的设计级决定。

§11 十一行覆盖全部生命周期 transition（含 request_action、abort、scope revision 这些非主线兄弟路径），每行带完整写序与 retry/resume/replay 反例，本地多写点显式折叠进 §6 前缀、外部行为叠加 §7/§9——无统一模板跳过窗口。§12.1 六维表按不变量逐一规划且自标“待实现/待验证，非 PASS”；§12.2 反切片条款（“不能把以上各行切成独立完成”）与“四变体×inline/worker 为基本组合、kernel 另做对照、不堆笛卡尔积”与 R3 §5 一致。E02 在 D02 矩阵中被正面修复（“incomplete process…即使 envelope 完整、artifact 发布受阻也不改写”），并要求常驻回归含成功/警告对照——该方案取代未提交实现中 A06 的 EXECUTION_NOT_PUBLISHABLE 伪产物失败路径，与工作清单“A06 需调整”处置一致，无矛盾但实施批次须按此对账。

4. 发现

WARN-1 · D03 自动推进的正向账本表示未指定、未入 §13。 §2.2 只定义了否定面（READY 不等待、不伪造 approved）和消费面（EXECUTION compile 引用两个 reviewed candidate/ref/SHA），但没有指定：READY 路由上人工门节点是否实例化（从 LiteFlowPrototypeKernelTest.returnsHumanGateAsTransitionCandidateWithoutCreatingAGate 推断可能是“不创建 gate occurrence、仅 BLOCKED 才入人门”，但这是推断不是设计）；reviewed candidate 在何处耐久固化（review 节点 refs？）；D06 写集是否包含该固化写点；CLI/API/UI 如何区分“已自动推进（程序固化）”与“已获人工批准”的资格显示。这是“严格授权与有界推进”边界的核心表示，属设计决定而非实施细节。修正：在 D03 增加一段明确 READY 路径的节点/路由/事实表示，并加入 §13 D03 的冻结条件。

LOW-1 · D02 contained-permission 关联是残留语义问题（有保守默认，已入 §13）——冻结前须给出“非必需”证据与 signal/义务的精确关联或明确不能容纳的范围。可留待 D02 冻结时解决。

LOW-2 · §6.3 reader BUSY 的投影适配未列 sibling。 “锁不可得返回 BUSY”是正确性优先的合理选择，但 CLI/API/UI/report 对 BUSY 与“持久化未完成”的展示是 I1 投影对等义务的新增面，§12.2 第一族 sibling 仅列“CLI/API/UI/report”未点名 BUSY/pending 两态。修正：在 §12.1 I1 行的 Cannot-bypass/Proven 中补“BUSY 与 pending 态的两个具体 UI 实例对照”。

LOW-3 · 复杂度检查通过但须守住两条线。 prepared mutation 与 D03 条款 id 迁移是两大重活；设计已拒绝更重方案（generation pointer、GoalContract、DSL）。风险在实施期 scope 膨胀：116 文件候选索引的诚实免责（“绝不等于需改 116 个文件”）应在批次对账时逐条落实为“改/不改+理由”。
