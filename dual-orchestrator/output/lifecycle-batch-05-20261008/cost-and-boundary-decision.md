本轮授权是 W01/D01 实施及离线验证。尚未修改产品或测试源码，未运行测试、native/provider、installer，未提交、启动额外 agent 或恢复历史样本。`baseline.json`、`before-source-sha256.json` 固定开工时已有 dirty 工作区；`source-checks.json` 固定本次核对的代码和设计材料。

## 1. 核实结果与判断强度

**已确认事实：**D01 不是“增加两个诊断字段”就能实现。冻结 §4 / freeze-details §2 要求决定时实际规则、规则版本和输入身份，后继失败与该决定配对，最后按可信依据区分矛盾、漂移、明确留后检查与 UNKNOWN。当前这套生产/消费接线不存在。现有严格拒绝和人工恢复不因此失效。

| 代码位置 | 已存在的能力 | 对 D01 尚不能提供什么 |
|---|---|---|
| `ReviewGateActions.resolve`（:40–55）、`RoutingEngine.resolveOpenGate`（:478–566） | 人工决定在 L 写会话内核验并路由；执行批准通过 `executionCandidate`；scope 修订有专用守卫 | 决定时逐规则的实际检查输入与覆盖记录 |
| `TaskContractProjectionVerifier.executionCandidate`（:380–425）和 `resolveExecution`（:157 起） | 批准前检查待审合同，dispatch 检查已批准合同；共享 `validateExecutionInputs`，严格保持批准/资格区别 | 分支采用的 `requireReady`、phase、gate 状态等语义不同，不能因 checker 类相同就视为同一检查 |
| `AuthoredStageLineageResolver`（:51–81、:167–174） | 读取事件，按 `through` 形成有界历史与 authored snapshot；重验既有 authority | 不能用整个 `events.jsonl` 的新旧 SHA 代替有界历史身份；正常追加事件本就会改变文件 |
| `ScopeRevisionRequestGuard.verify`（:20–104） | 严格核对 source、subject、基准文件、合同和 workspace；`require` 不满足则抛拒绝 | 实际使用的对象字段与文件依据没有作为逐规则诊断产物输出 |
| `AgentExecutionResultFacts`（:20–49） | 封闭的准备失败构造和相等核验，原原因/code、零 provider、MANUAL_ONLY | continuation 配对；直接附加任意 map 会被封闭核验拒绝，不能为接线放宽它 |
| `RecoveryAssessment`（:94–103） | 原准备失败原因保真，`retrySafe=false`，人工核对当前输入/批准或停止 | 四类诊断的可信证据消费；现有安全保守行为不是四类诊断已闭合 |

历史 `precondition-map.json` 的 200 项是五个指定类的词法清单，含 require/Failure.of/throw 等不同形式，不是 200 个已命名、已采集输入的业务规则。本轮另有四个当前类的 217 个调用候选，见 `lexical-inventory.json`。两者口径不同，**不能相减解释为新增 17 项，不能把本轮候选当作完成的一对一语义映射**。离线生成语义名称/编辑草稿已弃用；没有将错误正文或生成名称用于运行时。

**合理推测：**正确实现完整 D01，除字段、提交与投影外，还需要明确并接入共享检查的输入语义；范围超过原先口头描述的简单接线。没有实际实施计时、性能测量或报价，不能给出确定工期，也不能声称必然需要通用追踪平台。逐消费者的显式 typed 接线仍可能成立。

## 2. 已排除的捷径

1. 只凭动作被接受就写“全部后继前置 PASSED”：放大人工决定 authority，违反冻结契约。
2. 同 checker 类、同 subject 文件 SHA 就断言相同输入：漏掉 phase、候选/已批准、target occurrence、historyThrough 等真实检查条件。
3. 把整个 workstream 或事件文件哈希不同都解释为漂移：把正常完成 gate、追加路由、创建后继误报成输入失效。文件变化本身不证明非法漂移。
4. 给所有条件装通用追踪器、补成平台，再靠测试适配：尚无必要性/ROI 证明，不属于这次自动接受的实现方向。
5. 只接 UNKNOWN，仍宣布 D01 四分类完成：不符合真实生产和三类可触发的冻结验收。

这些是不可采用的实现捷径，不是对冻结语义的反驳。它们不能证明完整 D01 不可实现，只说明不能把它当成局部补丁推进。

## 3. 与“先跑通主流程”的关系

已存在 `HumanRequirementContinuationSequenceTest`：READY/BLOCKED 人工 revise、作者重做、独立复评、重新批准；clarify、缺 note 拒绝、错 subject 拒绝、写入中断和冷 ledger 续作均有用例。B04 独立评审和单轮 1701 项回归属于上一批证据，本轮仅核对用例源码，**未重跑，也不等于真实客户端主流程已证**。

D01 的收益是更早、更准确地定位“决定合法但后继拒绝”的新变体，减少人工排查。它本身不新增合法编码/自测/验收/交付能力；不能仅因补了自动解释，就称主流程成功率提高或 80% 已达成。后续仍有 W06 交付与 W08 总体覆盖/真实 Gate 的核对工作。本轮没有据此删除它们或自动开启下一批。

## 4. 提交用户的取舍（均未执行）

**作者建议：调整首版 D01，而不降低流程批准或业务验收。**

- 首版保留：实际决定 occurrence/subject、原失败 code、拒绝消费者与前置；仅在确实可证明的范围内提供配对诊断。依据不足明确 UNKNOWN、禁止自动重试，沿既有人工恢复处置。
- 不把全守卫的逐规则输入追踪和自动四分类设为首版主流程关闭条件；自动识别范围之外不猜矛盾、不伪造漂移、不虚报已检。
- 主流程的合法续作、非法拒绝、scope、身份、批准、独立复评、证据和交付验收不变；业务或外部执行结果不明仍人工裁定。
- 将四分类原义务如实保留为尚未完成，是否转后续工作须由用户批准，再修改 D01/主清单并做受影响范围评审。不能一边保留原冻结义务，一边宣布已满足。
- 再投入精细自动诊断的触发应来自真实主流程反复阻塞、现有诊断无法合理定位的案例；不按假想未来故障扩展平台。

这是产品范围取舍，**需要用户确认，不能把已有“80% 主流程优先”自动解释成撤销已冻结 D01**。如果用户选择保持完整 D01，则继续逐消费者的规则/输入接线，先审查输入语义，禁止全局文件哈希/错误正文捷径；不改成沙箱、权限平台或新增 authority。
