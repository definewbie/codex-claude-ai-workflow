2. 三个送审问题的独立回答

Q2 · pre-hook 是否值得在 adapter 方向内继续？——值得，且下一步可以精确化。 我核验时发现：run_pre_tool_use_hooks 与 PreToolUseHookResult 的定义不在当前快照中（全仓仅三处使用点）——评估所说的“执行失败如何解释尚未核实”，根因是定义模块未下载。这把“是否值得继续”变成一个一次性的离线问题：在同一 commit 补取 hook 运行器模块，回答三件事——① hook 执行失败/超时折算为 Blocked 还是 Continue（fail-closed 还是 fail-open）；② hook 配置从何处装配、是否受信任来源约束；③ 除默认 Function payload 外还有哪些调用面（MCP/custom）有/无 hook。若 fail-closed 且装配可信：pre-hook 成为第一个无需改引擎即可满足 collaboration "Enforced before" 的候选，且后续有界探针的安全案例优于 spawn 注入（Blocked 在创建路径之前返回，源码已证）。若 fail-open 或装配不可信：pre-hook 路线终止，§8.6 取舍不变。两个成本注意：hook 是 Dual 需维护的可执行内容（维护面与 patched acpx 同量级，应向用户显式列账）；既有全部 native 证据都是 hook 关闭状态下取得的，hook 开启是新政，须重做合法读取正向测试（不得靠拒绝一切完成只读）。

Q3 · 本地与托管网络工具是否正确区分？——正确且有双重强制点。 本地注册跳过（spec_plan.rs:1415-1432）与托管声明不构造（hosted_spec.rs:15-20）是两层独立证据；router 不把 WebSearchCall 当客户端工具分派——因此“伪造托管结果测本地拒绝”的排除是对的。对冻结而言：托管侧已有静态强制点 + 捕获请求未暴露声明的运行时证据，组合接近充分；本地侧归入 registry/hook 主线。

补充发现（评估未强调，影响 §8.6 权衡）· 子代理继承父权限快照。 apply_spawn_agent_runtime_overrides 表明：即使 spawn 执行，子线程在创建时继承父的 approval policy 与 permission profile 快照——即子代理的文件级写限制与父同源。这把 collaboration 缺口的最坏情形从“权限逃逸”降级为主要关乎 agent 数量/预算/协调身份（Dual 失去对委派的独占控制）。注意两个未验证点：该继承在子线程后续 turn 是否持续、子线程能否经 setMode 放宽。建议把这个事实（连同其未验证边界）写进 §8.6 选项矩阵——它可能实质改变“接受 native 自行委派”选项的成本评估。

3. 分级发现

F1（中）· hook 运行器定义缺失于快照——失败折算语义在当前材料内不可判。 已精确定位（全仓 grep 仅使用点）。修正：同 commit 补取该模块（纯离线、同一方法论、无新授权）。这是 pre-hook 路线唯一的下一 blockers。

F2（低）· 快照部分性应作为显式边界。 source-index 覆盖被引文件，但非全树；本评审即因快照不全区位了 F1。建议在材料边界声明中加一句“快照限于被引文件，跨文件定义需补取”。
