## 1. 问题、目标与归属

要回答的不是“工具会不会报错”，而是：**协议和参数均有效、D04 不允许的控制动作，能否被固定版本 native 的权限守卫在副作用前拒绝，同时保留合法读取。** 单个查询、畸形参数或错误协议的拒绝不回答这个问题。

Definition 仍为 D04 能力上限；Instance 仍为 Dual 已批准工作及运行身份；Execution 为 native 的具体请求和结果。运行时 SoT 是 native 的实际分派/拒绝/执行事实。离线设计、模型桩、汇总器和 CC 只解释证据，不创造批准或权限事实。未来 adapter/runtime 是唯一产品消费链，本轮不增加模型层、平台、权限机制或持久化状态。

接受本次 CC 的材料 PASS、D04 不冻结；[评审原文](cc-review.txt)保留。F1 的“注入探测”可作为研究方法，但其零副作用及可直接填满 Enforced before / Cannot-bypass 的推论不成立。F2 的 never+readOnly 拦截只是待证假设。F3 保持未决；原生 Rust 源码审计本身属于静态核验，并不天然需要新增 authority，缺的是对应版本源码及构建关系。管理员权限变更则仍须用户决定。

## 2. 已核实契约与不可猜测项

已从前轮实际 request 提取 6 个 collaboration 工具，全部声明为 `type=function`、`strict=false`；[原始契约摘录与 SHA](tool-contract-evidence.json)可追溯。`spawn_agent` 要求 task_name、message；`list_agents` 无必填参数。因此不得直接复用 functions.exec 的 custom_tool_call wire 形状，也不得假设 strict=false 表示 native 必然做或不做参数校验。

仍缺：与固定 native 对应的 Responses **响应项** wire 契约及消费者（命名空间表示、arguments 编码、call_id/result 对应）、错误阶段/原因的可靠识别、分派守卫与副作用的实际顺序。工具声明不是完整 wire 协议；不能只把 type 改成 function_call 就声称已解决。网络工具的托管/本地执行路径与返回契约也未确认，不能套用 collaboration 的编码。

| 有效 spawn 因额度/深度已满而拒绝 | 当前额度/前置拒绝 | 额度恢复或深度改变后仍可能允许创建，不是 D04 禁用 |

结果必须关联完整 request、实际 call、匹配 result、配置/版本、错误阶段和来源。权限原因如无可靠机器字段，可以通过可追溯同版消费代码解释，但不能仅靠正文关键词。不能因“不知道错误阶段”归入成功拒绝。

## 5. 零副作用前置与 transition / 失败切面

fresh HOME、本地模型桩、假凭据、只读文件沙箱，都不能单独保证 native 不创建内部 agent、消耗执行槽或调用托管网络工具。事后 watchdog/kill 能限制后续损失，不能撤销首次副作用。把一次调查的所有动作塞进一个批量响应，会失去首错停止能力，不采纳 CC 的“一会话同时测完”作为默认设计。

| pre-state 与触发 | write / side effect 顺序 | 失败、停止及重启语义 |
|---|---|---|
| 本轮仅离线材料 | 读取旧证据→生成新设计/快照→核验链接和身份 | 写失败不改旧包，不据半份新材料作准入 |
| 未来启动前（目前未准入） | 核验同版协议/安全前置/授权/Gate/预算→保存准备记录→启动 native | 任一未满足即零调用；不得复用旧预算 |
| 首个动作前 | 保存请求及待发响应→检查精确动作、协议和数量→仅发一条 | 本地文件写入或判据检查失败则不发送；不为便利改动作参数 |
| native 接收 | 解码→参数/权限/资源等检查→分派→可能副作用→结果 | 这里只列逻辑环节，真实先后顺序待同版消费者核验；不得假设权限检查一定最先 |
| 收到结果 | 保存原始返回→关联 call/阶段/来源→评估→决定是否允许下一条 | 拒绝原因不明、成功触发禁止动作、transport 异常即停止后继；不中途宽松改分类 |
| 发送后中断/结果落盘失败 | 可能已分派或产生副作用 | 记录 UNKNOWN，保留现场，不重试、不自动 resume/replay、不以旧 call_id 重发 |
| 重新启动调查 | 读取已保存证据和剩余授权 | 不续执行 pending 注入；新旧 binary/config 不符则 INVALID，先重新设计/授权 |

本轮不新增保护机制。未来若要靠外层拦截来保证零副作用，应先区分它是测试支架还是生产 authority；它可以保护调查，但不能独自证明 native 拒绝。若需要改变执行权限、允许真实代理或外网、修改引擎/分工，停止交用户决定。

## 6. 非可执行 Gate 草案

以下各空缺都是未满足的启动条件，不是本次申请。**Run authorization＝NONE；运行预算未申请；允许 native/工具/模型/agent 调用数＝0。**

Verification Gate:
- Target: 待锁定单一入口及可区分的权限假设；不使用“看到拒绝即通过”。
- Source of truth: 固定 native 的实际 call/result 与同版分派/守卫代码或可核对的运行事实；测试桩只提供输入。
- Trigger precondition: 正确 wire、有效参数、准确运行身份、特定动作副作用前置边界已证，且存在足够安全且有判别力的候选。**当前未满足。**
- How precondition is checked before run: 先给出可定位源码/构建或原生协议锚点，确认动作经过目标守卫；离线故障注入检查分类与禁止后继，再独立核对 Gate。不得由未来测试结果反推启动前已安全。
- PASS: 仅对选定能力切片，合法必要能力仍成立、有效禁止动作在副作用前被明确权限规则拒绝，证据完整；其他入口保持未证。
- FAIL: 禁止副作用发生、资格/能力上限不能强制、或合法必要能力被破坏；立刻停止后继。
- INVALID: wire/参数/错误来源/版本不符合目标，缺失结果或安全前提无法确认；保持现场，不能称部分成功。
- Stop-loss: 动作/会话/请求/时间上限尚未申请，不得启动；以后按动作逐条等待与判定，禁止批量连发及失败自动重试。
- Run artifact freshness: 未来固定 native/host/adapter/config/schema/Gate/driver SHA 与新目录；任一漂移重新核对，不覆盖旧证据。
