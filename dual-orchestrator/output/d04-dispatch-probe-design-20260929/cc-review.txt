2. 独立接口排查（回答“是否遗漏”）

我沿四个面自行排查：

1. 协议面：ThreadStartParams 根级与 tool/agent/mode 相关的字段仅有 dynamicTools（只增不减，作者已判）、multiAgentMode（弃用+ignored，作者已判）、sandbox/approval 类（文件/执行域，前轮已证）。无原生工具削减字段——协议面无遗漏。
2. 二进制线索面：binary-interface-hints.json（32K）中无 CODEX_* 环境变量式特性开关线索；multi_agent 字符串即已被排查的 features 配置路径。无环境变量遗漏。
3. 配置面：作者已覆盖 features 布尔/表结构、命名空间排除、并发上限、根级白名单、max_depth 线索、web_search。结合官方参考的 MCP/插件作用域判断，无新配置候选。
4. adapter 面：作者核对 new/resume/fork 汇合与每 turn policy，未见覆盖内建协作工具的 veto（adapter-interface-map）。我没有发现反例。

判定：接口层面无遗漏，作者的否定性结论成立，且其边界声明（“不推导 Codex 无法限制、不推导已能越权”）恰当。

3. 发现

F1（主要发现）· 遗漏了一个有界验证方法：注入探测。 前轮（native-boundary-review）已证实的方法论——本地 Responses 捕获真实工具契约后注入 custom_tool_call——正是为“测 native 分派层对指定调用的真实反应”而生，且已在 Write/apply_patch/escalation 上产出决定性证据。本轮对 collaboration 命名空间只做了装配层观察（请求里有什么），未做分派层测试（调用会怎样）。两个零副作用探针：
- collaboration.list_agents（纯查询，无 agent 时返回空或拒绝）——若被硬拒，即命名空间级强制证据；若执行，则表面存活坐实。
- spawn_agent 带畸形参数——若触发参数校验拒绝，近似得到“隐藏控制命令在副作用前被拒”的 Cannot-bypass 证据而不创建任何 agent。
  一次有界捕获会话可同时覆盖 LOW 级的 web_search 隐藏分派探针。代价：一次新的捕获预算（需你授权）；风险：低（桩环境、fresh home、参数畸形不触发真实委派）。这是“不改 authority/引擎/分工”前提下唯一剩下的证据路径。

F2（边界确认）· never+readOnly 是否经由审批语义拦截协作工具——这是 F1 探针恰好能回答的机理问题（若协作工具需审批，never 自动拒绝即硬限制），作者未提此假设；不单列发现，归入 F1 的判别目标。

F3（LOW）· 管理员 requirements 与 Rust dispatcher 实现两层：作者已声明未穷尽；前者属 authority 变更（你的决策域），后者是源码级核验（超出静态边界）。维持登记即可。

4. 链重建与六维

准备（binding，待实施）→装配（本轮已观测：配置不达排除目标）→非法调用（未测——唯一断点，即 F1 目标）→消费/收尾（实施后义务）→中断恢复（D06/D07）。六维中 Enforced before（协作/网络副作用前限制）与 Cannot-bypass（隐藏控制命令硬拒绝）两格为空，与作者自评一致——这不是材料缺陷，是诚实的空格；F1 正是填这两格的最短路径。
