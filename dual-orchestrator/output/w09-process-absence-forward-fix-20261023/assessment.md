# 历史 PID 重查：离线候选与受影响评审入口

本轮完成的是测试辅助脚本的最小修正：首次准备仍查进程；后续复用程序已记录且固定输入核验通过的“旧进程已退出”事实，不永久追查旧号码。Java Dual、原发行、业务批准与账本均未修改。离线验证成立；完整新 Gate 装配、真实运行及主流程完成均未证明。

## 已确认事实与推测边界

第八例停止在辅助 runner 的进程前置检查，未创建第22步目录、未启动该步 Java。原记录中62个旧 PID 已经成功查表确认缺席并固定于 old-execution-recheck.json；后续每步仍重新检查这62个号码，触发时报告83976存在。触发当刻的命令、启动时间与身份没有保存。稍后的完整只读观察中该号码已不在。

因此，号码重复分配是合理解释，不能称为已证明的具体身份因果。已证明的设计问题是：**曾成功确认旧进程结束后，仍把其号码永久当作未决旧执行。**候选不为83976写特例，也不依赖猜测该号码当时属于谁。旧 Gate 按其原规则停止是正确执行，本轮不重分类或挽救旧样本。

当前领域仍为 RUNNING，node-plan-decision-026 READY；固定用量848,242 token、10请求。EXECUTION未编译、无产品写入授权。实验停止及 stop-required 保留，余量不成为本轮续作许可。

## 最小接线

1. `prepare-offline.py`：把原始清单作为待检查目标，剥离输入的 absent 标记，实际调用原严格检查。成功后先写观察、再写程序确认记录；任一写失败不创建 fixture。首次输入自行填写 absent=true 没有豁免作用。
2. `pre-dispatch-recheck.py` / `run-one-step.py`：保留原 frozen_check 次序，只消费固定 old-execution-recheck.json。已确认记录不再列入待查集合；未确认记录仍走原严格读表。
3. `process_check.py`：共享上述集合划分。读表失败、EPERM、空表、畸形/重复行、超时仍 UNKNOWN；未确认目标出现仍 PRESENT。两者都阻断后续动作。原严格检查与只读 CLI 行为不变。
4. 全部记录已确认时返回 `NO_UNRESOLVED_PIDS`，不是伪造本次成功读表的 ABSENT。零未决目标不等于所有子进程或远程作业已停。

只变更4个候选辅助文件及1个测试文件。复用既有记录与 SHA 核验，无新 schema、Java 类、锁、服务、进程监督平台或持续扫描。候选副本保留原文件的历史路径常量，且没有配套授权与完整 Gate 输入，**不得直接运行三个顶层脚本**；受审内容是差异及离线验证。未来装配必须使用独立目录并固定新字节，不能覆盖原第八例包。
