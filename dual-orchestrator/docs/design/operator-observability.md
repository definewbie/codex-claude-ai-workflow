# Operator Observability

This document describes the current observability model for CLI, API, and the
operator panel.

## Goal

The operator experience should answer one question quickly:

> Where is the workstream now, why did it stop, and what should I do next?

The answer must be the same whether the user reads CLI output, calls the local
API, or opens the operator panel.

## Read Models

The UI does not parse raw Agent logs directly. It consumes stable ledger read
models:

| Read model | Purpose |
|---|---|
| `workflow/current.json` | Current workflow status and active nodes. |
| `timeline.json` | Ordered node/gate progress for lifecycle navigation. |
| `metrics/workstream-metrics.json` | Node, gate, iteration, duration, and provider run counts. |
| `reviews/*.json` / `.md` | Human gate packet and recommended review action. |
| `recovery/current-failure.json` / `.md` | Current failure explanation and recovery hint. |
| `reports/workstream-summary.md` | Human-readable lifecycle recap. |
| `runs/*/outputs/*.contract.json` | Validated Agent artifact sidecars. |

These read models are generated by the runtime and ledger. The operator panel is
intentionally lightweight.

The local server also exposes a lightweight Server-Sent Events stream:

```text
GET /api/workstreams/<workstream_id>/stream?workdir=<effective_workdir>
```

The stream sends `overview` events backed by the same API overview read model,
plus heartbeat events when nothing changed. It is a projection channel only; it
does not own workflow state and does not infer progress from raw logs.

## CLI First

`dualctl trace` is the primary operator command. It folds status, timeline,
attention items, final acceptance, repair loops, key artifacts, and next actions
into one screen.

Trace and runs are observation projections, not workflow executors. If a
historical `runs/<run_id>/run.json` file is missing or damaged, they should show
a metadata warning instead of failing the command or reinterpreting a completed
workstream as failed. Only explicit `inspect --run <run_id>` performs strict
inspection of one run metadata file.

Other commands are deeper tools:

```bash
dualctl status --workdir <effective_workdir> <workstream_id>
dualctl timeline --workdir <effective_workdir> <workstream_id>
dualctl review show --workdir <effective_workdir> <workstream_id>
dualctl recovery show --workdir <effective_workdir> <workstream_id>
dualctl runs --workdir <effective_workdir> <workstream_id>
```

The CLI and UI should use the same concepts and labels. The UI should not invent
a second workflow vocabulary.

## Operator Panel

The operator panel is a local single-user tool. It is not a multi-user product
or hosted dashboard.

Starting with the P2 operator work, the panel has two views:

| View | User | Purpose |
|---|---|---|
| Operator Console / Task View | end user, reviewer, operator | Follow task progress, approve human gates, handle recovery, and confirm delivery. |
| Management Diagnostics | dual users, developers, debuggers | Inspect ledger facts, raw node ids, RCA, CLI commands, token/cost, and recovery evidence. |

Prototype: [operator-console-prototype.html](operator-console-prototype.html).
Implementation plan: [operator-console-implementation-plan.zh-CN.md](operator-console-implementation-plan.zh-CN.md).

The first screen prioritizes:

1. lifecycle progress;
2. current status and stop reason;
3. next action;
4. attention items;
5. human review packet when a gate is open;
6. recovery summary when a failure is active;
7. grouped timeline and metrics.

Actions are contextual. A human gate should show review evidence and decision
buttons together. Debug details, raw packet content, and raw ledger paths should
be secondary.

The task view should not foreground raw JSON, internal node ids, scheduler
vocabulary, or full ledger paths. Those belong in Management Diagnostics.
Diagnostics must not be a stripped-down view; it should be organized like an RCA
surface:

- symptom;
- impact;
- timeline;
- current hypothesis;
- evidence chain;
- immediate mitigation command;
- verification after repair;
- prevention notes;
- raw facts.

This keeps the end-user path understandable while preserving enough information
for dual users to diagnose and fix issues.

As of P1/P2 closure work, the panel intentionally keeps only one primary
workflow action visible by default. Max-step tuning, manual refresh, scheduler
tick, and auto-recovery are advanced controls. This avoids making normal
operators choose between internal mechanics before they understand the current
state.

The Scheduler Tick control has an explicit recovery option:

- unchecked: only `RUNNING` workstreams are resumed;
- checked: `WAITING_FOR_RECOVERY` workstreams are considered, but only
  retry-ready runtime failures are retried and resumed.

This option consumes `RecoveryAssessment`. It does not auto-fix artifact
contracts, semantic disputes, or human decisions.

When the background scheduler is enabled, it can also run an optional local
notification command for gate, failure, and completion boundaries. The hook is
disabled by default and receives environment variables such as
`DUAL_WORKSTREAM_ID`, `DUAL_STATUS`, `DUAL_EVENT`, `DUAL_WORKDIR`, and
`DUAL_ACTIVE_NODE`. Notification failure is reported in scheduler status but
does not change workflow state.

## Human Gate Semantics

Human gates are real pause points. Smoke scripts may auto-approve gates for
benchmark automation, but normal operation expects a person to read the review
packet before choosing:

- approve and continue;
- request revision with feedback;
- complete the workstream;
- stop and inspect.

The packet should show the minimum evidence needed to make that decision:
TaskContract, verifier decision, must-fix items, relevant Git evidence, known
risks, and recommended checks.

The packet is not a raw Agent log dump. `reviews/*.md` / `.json` should
foreground structured sidecar summaries, risks, missing evidence, must-fix
items, and artifact paths. Full stdout/stderr remain available as debugging
references, but they should not be embedded into the first human-review screen by
default.

## Timeline Semantics

Timeline order is chronological and grouped by lifecycle stage. The timeline is
not a log dump. It should make progress visible:

```text
intake -> contract -> design -> plan -> implementation -> self-test -> acceptance -> delivery -> handoff
```

Within each group, nodes retain timestamps and status. Failed or waiting nodes
should be visually obvious.

## Metrics

Metrics are currently lightweight:

- node counts by status;
- agent run counts by provider;
- completed/failed/prepared agent runs;
- recoverable failures;
- total and average provider duration;
- gate and iteration counts;
- longest node duration.

Token and cost metrics are recorded when the acpx adapter can match the current
prompt to a session stream usage event. Those measured records use
`source=acpx_stream`. When measured usage is unavailable, projections may show
`source=artifact_estimate`, derived from prompt/output/transcript metadata.
Estimated usage exists to explain relative cost and context growth for old or
incomplete runs; it must not be presented as provider billing truth.

The task view should show a lightweight token/cost card so the operator can see
whether a task is becoming expensive or context-heavy. Management Diagnostics
can show more detail: prompt tokens, completion tokens, budget ratio, estimated
cost, and source of the data.

These metrics are for observation and tuning only. They do not participate in
workflow routing and do not replace artifact contracts or recovery decisions.

The same source labels should appear in CLI (`runs`, `trace`) and the operator
views. If a projection cannot distinguish measured from estimated usage, it
should hide the number or label it as estimated instead of silently mixing the
two.

## Project And Task Entry Registry

The operator UI needs to find tasks that were started by CLI or autorun without
asking the user to paste an effective workdir each time. The source of truth is
split deliberately:

- `~/.dual/operator-workspaces.json` is a local entry index for known projects
  and recent workstream workdirs.
- Each workstream ledger remains the source of truth for lifecycle status,
  gates, recovery, artifacts, metrics, and delivery state.
- Browser localStorage may remember the last selected project or task, but it
  must not be the task registry.

The registry is multi-project from the beginning: a project is one local Git
repository plus its default `<repo-name>-agent-runs` pool. Selecting a project
causes the UI to query the ledger projections for that project and its
worktrees. The registry can be rebuilt or pruned without changing workflow
history.

## Loop Semantics

The dual lifecycle is not a one-shot linear pipeline. A goal may go through
bounded semantic repair loops:

```text
goal -> design/implement/acceptance -> verifier reject -> bounded repair -> acceptance
```

The UI should keep the linear lifecycle progress bar because it is easier to
understand, but it must also expose lightweight loop context:

- current round, such as `implementation repair round 2/3`;
- loop history, showing who triggered each loop, why the workflow returned to an
  earlier phase, and what the current result is;
- semantic repair, runtime retry, and human revision must remain separate.

Management Diagnostics may show full iteration ids, trigger artifacts, previous
decisions, loop reasons, and max rounds. The task view should show only the
summary needed for human judgment.

## Observed Usability Gap

A private production-like run exposed a usability issue: the operator panel can
still show generic English stopped/retry copy, for example:

```text
Workflow is stopped. Fix the cause if needed, then Retry marks the active node ready to run again.
```

That wording is not friendly for the expected operator, and it can collapse
different states into the same mental model: an aborted old workstream, a new
workstream waiting for human review, and a real recovery failure should not all
look like the same “stopped” state.

Future UI/CLI copy should follow these rules:

- operator-facing prompts should have Chinese-first wording where appropriate;
- `WAITING_FOR_HUMAN` should read as waiting for human review, with the review
  packet and approve/revise actions foregrounded;
- `WAITING_FOR_RECOVERY` should read as needing recovery, with the failed node,
  reason, recommended action, and auto-recovery eligibility visible;
- `FAILED` / `ABORTED` should read as failed / aborted and should not
  automatically suggest Retry;
- when a newer workstream exists for the same task, the operator should be
  guided to open the latest workstream.

## Future Direction

The next useful step is not a heavier UI framework. It is stronger consistency:

- CLI trace, API overview, and operator panel should render the same attention
  items.
- Completed workstreams should expose a completion audit and reject accidental
  resume/retry/approve actions.
- Stale running should be an explicit recovery action, not a hidden button or a
  silent rerun.
- Failure/recovery summaries should remain structured.
- Review packet layout should keep improving around real human decisions.
- Real-time push uses the overview SSE stream. File watching can be added later
  only if the current read-model stream is not enough.

## TODO: Interaction Smoothness

Real runs exposed a larger operator-experience issue: the workflow currently
stops too often at human checkpoints. The operator has to keep clicking approve,
retry, or run, so the lifecycle still feels like a manually driven sequence of
segments instead of a system that runs autonomously and asks for human judgment
only at meaningful gates.

Future design work should revisit:

- which gates truly require human product, architecture, or delivery judgment;
- which gates are only process or format checks and should be handled by the
  system automatically;
- which verifier feedback can enter a bounded automatic loop instead of forcing
  manual handoff every time;
- what should terminate an automatic loop, such as max rounds, semantic
  conflict, insufficient evidence, or external tool failure;
- how the operator panel explains why the workflow stopped and what the
  recommended next action is, rather than only exposing buttons;
- how both CLI and UI can support run-to-next-human-decision without requiring
  users to understand every internal node.

The goal is not to remove human review. It is to reserve human review for
places where judgment is actually needed: requirement boundaries, design trade
offs, acceptance disputes, and delivery confirmation.

P1/P2 scope should now focus on:

- public repeatable benchmark evidence instead of private exploratory P0 cases;
- fewer first-screen controls;
- stronger current-vs-historical review packet separation;
- one shared answer across `trace`, API overview, and the panel.
