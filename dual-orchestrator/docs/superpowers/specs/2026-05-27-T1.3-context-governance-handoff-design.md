# T1.3 Context Governance & Handoff Sidecar Design

## 1. Problem Statement

`ContextBuildPackageHandler` 当前的问题：

1. **总上下文不可控。** 7 个 section 各自独立截断到 `max_snippet_chars`（默认 4000）。7 × 4000 + markdown 头部 ≈ 35k 字符，直接塞进 agent prompt 可能超出 context window。
2. **prompt 进入 agent 前缺少总预算治理。** handler 渲染完直接写文件，没有全局 budget 校验。
3. **substring 截断破坏上下文语义。** 超长 section 用 `substring(0, max)` 硬切，可能切断 markdown 结构（表格、代码块、列表），agent 拿到的是不可用的碎片。
4. **workflow node 对 context 的依赖不同。** 所有 profile 用同一套截断逻辑，但 implementation node 需要完整 requirement + code context，review node 需要完整 feedback + iteration history。当前无法表达这种差异。
5. **handoff 是纯文本。** 下一阶段的 handler 无法从 handoff 中提取结构化信息（changed files、open risks），只能读整个 markdown。

## 2. Design Goals

- total context budget 可控，超预算时有明确的降级路径而非破坏性截断。
- section-aware degradation：每个 section 有自己的降级策略（不是统一 substring）。
- profile-aware context requirements：不同 profile 声明不同的 section 依赖和优先级。
- degradation 显式可见：agent 能看到哪些 section 被降级、用了什么策略、原始数据在哪。
- requirement section 不参与普通降级，超出硬上限直接 fail。
- V1 只实现 implementation profile，其余 profile 保持当前逻辑。
- handoff.json sidecar 由 handler 从 markdown 解析生成，agent 不需要直接输出 JSON。

## 3. Non-Goals

- 不实现动态预算算法（V1 用静态 priority 排序分配）。
- 不实现 KEY_HUNKS patch hunk 选择（V1 用 DIFF_STAT：changed files + diff --stat）。
- 不迁移所有 profile 到新 schema（V1 只迁移 implementation，其余保持 `switch` 逻辑）。
- 不让 agent 直接输出 handoff.json（handler 从 markdown 解析生成）。
- 不引入外部 summarization 或 LLM compression。
- 不做 BuiltinHandlerTest 重构。
- 不引入动态预算算法、adaptive compression、semantic ranking 或 token-aware budgeting。

## 4. Context Governance Schema

### 4.1 Degradation

```java
enum Degradation {
    FULL,           // 完整输出
    SUMMARY,        // deterministic 结构化压缩（见约束）
    LATEST,         // 最近 N 条完整记录
    DECISION_ONLY,  // 只保留 decision/outcome 字段，丢掉 reason 全文
    DIFF_STAT,      // changed files 列表 + diff --stat（约束：禁止读取 full patch）
    POINTER_ONLY    // 只输出文件路径指针，不输出内容
}
```

**SUMMARY 约束：** SUMMARY 是 deterministic 的结构化压缩。禁止调用 LLM。禁止 runtime summarization。必须由 handler 从结构化数据中提取可确定的字段（文件名、标题行、元数据 key-value）。不等于"取前 N 行"。

**DIFF_STAT 约束：** DIFF_STAT strategy MUST NOT load or render full diff.patch content. Only changed file names (from `git-status-short.txt` or `changed-files.txt`) and `diff.stat` output are allowed. Implementation must not read `diff.patch` at this degradation level.

### 4.2 DegradationPolicy

```java
record DegradationPolicy(
    Degradation strategy,
    int maxItems       // LATEST(3), DECISION_ONLY(5) 等。0 = unlimited
)
```

### 4.3 MissingPolicy

```java
enum MissingPolicy {
    FAIL,        // section 数据源不存在时 context build fail
    SKIP,        // 不存在时跳过，不输出该 section
    PLACEHOLDER  // 不存在时输出占位符 "(not available)"
}
```

### 4.4 OverflowPolicy

```java
enum OverflowPolicy {
    FAIL,            // 超预算时 fail（CRITICAL section 专用）
    DEGRADE,         // 按 degradeTo 策略降级渲染
    DROP_OPTIONAL    // 非必需 section 直接丢弃，不输出
}
```

### 4.5 Priority

```java
enum Priority { CRITICAL, HIGH, MEDIUM, LOW }
```

### 4.6 SectionRequirement

```java
record SectionRequirement(
    String section,
    MissingPolicy missingPolicy,
    Priority priority,
    DegradationPolicy degradeTo,
    OverflowPolicy overflowPolicy,
    int softBudget
)
```

- `missingPolicy=FAIL`：数据源必须存在，否则 context build fail。这替代了原先的 `required` 字段。
- `missingPolicy=SKIP`：数据源不存在时跳过，不输出该 section。
- `missingPolicy=PLACEHOLDER`：数据源不存在时输出占位符 "(not available)"。
- `softBudget`：预算规划参考值，不是截断线。section 渲染时尝试控制在 softBudget 以内，但不保证精确。

### 4.7 ContextBudget

```java
record ContextBudget(
    int totalBudget,
    List<SectionRequirement> sections
)
```

|---|---|---|---|---|---|
| requirement | FAIL | CRITICAL | FULL(0) | FAIL | 10000 |
| input_artifacts | PLACEHOLDER | HIGH | SUMMARY(0) | DEGRADE | 6000 |
| iteration_history | SKIP | MEDIUM | DECISION_ONLY(5) | DEGRADE | 3000 |

| ledger_pointers | SKIP | LOW | POINTER_ONLY(0) | DROP_OPTIONAL | 500 |

- `requirement` 的 `overflowPolicy=FAIL`：如果 requirement 单条就超出 totalBudget 硬上限，context build fail。softBudget=10000 是预算规划参考，不是截断线。
- `git_evidence` 的 `DIFF_STAT`：只输出 changed files 列表 + `diff --stat`，不包含 patch hunks。KEY_HUNKS 留到后续。
- `ledger_pointers` 的 `DROP_OPTIONAL`：超预算时直接丢弃，不降级。

## 6. Rendering Pipeline

### Phase 1: Load profile requirements

根据 `profile` 配置（来自 node config）加载对应的 `ContextBudget`。所有 6 个 profile（product_review / architecture_review / plan_review / implementation / acceptance / full）均通过 `ContextProfiles` 注册表使用 governed pipeline。`include_sections` 配置覆盖会走旧 `renderPackage` 路径以保持向后兼容。

### Phase 2: Resolve section availability

遍历 `SectionRequirement`，检查每个 section 的数据源是否存在：
- `missingPolicy=FAIL` 且数据不存在 → fail
- `missingPolicy=SKIP` 且数据不存在 → 标记该 section 为 SKIP
- `missingPolicy=PLACEHOLDER` 且数据不存在 → 标记该 section 为 PLACEHOLDER

### Phase 3: Plan budgets

1. 将所有 section 按 priority 从高到低排序（CRITICAL → HIGH → MEDIUM → LOW）。
2. 按排序依次尝试为每个 section 分配 softBudget，累计已分配预算。
3. 如果累计已超过 totalBudget → 从当前最低 priority section 开始应用 overflowPolicy：
   - `DEGRADE` → 降级渲染（标记该 section 使用 degradeTo 策略）
   - `DROP_OPTIONAL` → 直接丢弃该 section
   - `FAIL` → context build fail
4. 重新计算剩余预算，继续尝试分配下一个 section。
5. 重复步骤 3-4 直到所有 section 都已处理，且总预算 ≤ totalBudget。
6. 如果所有非 CRITICAL section 都已 DROP 且仍然超预算 → FAIL。

V1 不做复杂动态分配。按 priority 排序 + softBudget 预扣 + 逐级降级。

### Phase 4: Render sections with degradation

每个 section 按其 degradeTo 策略渲染：

| Degradation | 渲染行为 |
|---|---|
| FULL | 当前逻辑不变 |
| SUMMARY | handler 从数据中提取结构化摘要。例如 input_artifacts → 只输出每个 artifact 的文件名 + 前几行摘要，不输出完整内容 |
| LATEST(N) | 只取最近 N 条记录，完整输出每条 |
| DECISION_ONLY | 只输出每条 iteration 的 triggerAction + decision outcome，不输出 reason 全文 |
| DIFF_STAT | 只输出 changed files 列表 + diff --stat 输出，不输出 diff.patch 全文 |
| POINTER_ONLY | 只输出文件路径 |

### Phase 5: Validate total budget

所有 section 渲染完成后：
- 计算总字符数
- 如果 ≤ totalBudget → 通过
- 如果 > totalBudget → 从最低 priority 的非 CRITICAL section 开始降级或 DROP，直到 ≤ totalBudget
- 如果所有非 CRITICAL section 都 DROP 了还超 → FAIL

### Phase 6: Emit Context Governance summary

在 context package 开头输出 Context Governance summary table（见 Section 7）。

## 7. Context Governance Summary Format

```markdown
# Context Package

- Workstream: ws-001
- Builder Node: context.implement_claude
- Target Node: implement.claude_implement
- Generated At: 2026-05-27T12:00:00Z
- Purpose: Package approved plan and review history for Claude implementation.
- Total: 10.2k / 24.0k budget

## Context Governance

| Section | Level | Degraded | Original | Current |
|---|---|---|---|---|
| requirement | full | - | 2.1k | 2.1k |
| input_artifacts | summary | yes | 8.3k | 1.2k |
| iteration_history | decision_only | yes | 4.7k | 0.8k |
| human_feedback | latest(3) | no | 1.1k | 1.1k |
| recent_agent_outputs | latest(2) | yes | 12.3k | 3.8k |
| git_evidence | diff_stat | yes | 6.2k | 0.4k |
| ledger_pointers | pointer_only | no | 0.3k | 0.3k |

Degraded sections have full data at their original paths listed below.

## User Requirement
...
```

- `Level` 列显示该 section 使用的 degradation 策略名称。
- `Degraded` 列：`yes` = 从完整数据降级，`no` = 完整保留，`-` = 不适用（如 requirement）。
- `Original` = 该 section 原始数据大小，`Current` = 渲染后大小。

## 8. Handoff JSON Sidecar

### 8.1 生成方式

`PromptGenerateNextStageHandler` 在读取 handoff markdown 后，解析关键 section 并生成 `handoff.json` sidecar。agent 不直接输出 JSON。

解析规则（从 `stage-claude-handoff.md` prompt 模板定义的 section 结构提取）：
- `## Completed Work` 下的列表项 → `completedWork` 数组
- `## Changed Files` 下的列表项 → `changedFiles` 数组
- `## Open Risks` 下的列表项 → `openRisks` 数组
- `## Verification State` 下的内容 → `verificationState` 字符串

如果某个 section 不存在或为空，对应字段为空数组或空字符串，不 fail。

### 8.2 Schema

```json
{
  "schemaVersion": 1,
  "workstreamId": "ws-001",
  "stageId": "stage-design",
  "iterationId": "iter-001",
  "sourceHandoffPath": ".agent/workstreams/ws-001/runs/run-42/outputs/stage-claude-handoff.md",
  "completedWork": [
    "Designed the API schema",
    "Created component architecture"
  ],
  "changedFiles": [
    "src/main/java/dev/dual/runtime/handler/ContextBuildPackageHandler.java"
  ],
  "openRisks": [
    "Rate limit behavior under load"
  ],
  "verificationState": "self_test_passed",
  "acceptanceOutcome": "ACCEPT",
  "generatedAt": "2026-05-27T12:00:00Z"
}
```

**Schema contract：** Consumers must ignore unknown fields. This allows forward-compatible schema evolution without version branching.

**`sourceHandoffPath`** points to the original handoff markdown artifact that was parsed to produce this JSON. Used for replay, debug, regeneration, and traceability.

### 8.3 消费者

下一阶段的 `ContextBuildPackageHandler` 检查 handoff.json 是否存在：
- 存在 → 用结构化数据做更精确的 context 装配（例如 SUMMARY 策略直接取 `changedFiles` 数组，不解析 markdown）
- 不存在 → 回退到当前 markdown 解析逻辑

### 8.4 存储位置

```
.agent/workstreams/<ws>/artifacts/next-stage/handoff.json
```

与 `next-stage-prompt.md` 同目录。

### 9.2 测试链路

**链路 1: context build → decision**

```
准备 requirement.md + agent output (含 dual-control block)
→ ContextBuildPackageHandler.execute()
→ 验证 context package 文件存在，包含正确 section
→ ReviewDecisionHandler.evaluate()
→ 验证 decision 结果正确
```

**链路 2: handoff → next stage prompt + handoff.json**

```
准备 handoff markdown (含 Completed Work / Changed Files / Open Risks)
→ PromptGenerateNextStageHandler.execute()
→ 验证 next-stage-prompt.md 存在
→ 验证 handoff.json 存在且结构正确
→ 验证 completedWork / changedFiles / openRisks 字段被正确提取
```

**链路 3: budget governance under oversized inputs**

```
准备 requirement.md + 大量 agent output（总计 > totalBudget）
→ ContextBuildPackageHandler.execute() with profile=implementation
→ 验证 context package 开头有 Context Governance summary
→ 验证 LOW priority section 被降级（Level 列 != full）
→ 验证总长 ≤ totalBudget
→ 验证 requirement section 完整保留
```

**链路 4: requirement 超硬上限 fail**

```
准备超长 requirement（> totalBudget）
→ ContextBuildPackageHandler.execute()
→ 验证 FAILED，outcome 包含 budget exceeded
```

## 10. Acceptance Criteria

1. `implementation` profile 下生成的 context package 总长 ≤ totalBudget（默认 24000）。
2. context package 开头包含 Context Governance summary table。
3. requirement section 完整保留，不参与降级。requirement 超总预算时 context build fail。
4. LOW priority section 可被降级或 DROP_OPTIONAL。
5. 降级不是 substring，而是按 Degradation 策略渲染。
6. handoff.json 能从 handoff markdown 解析生成，字段结构正确。
7. handoff.json 不存在时，ContextBuildPackageHandler 回退到 markdown 解析。
8. 非 implementation profile（product_review, architecture_review, plan_review, acceptance, full）行为不变。
9. 测试覆盖：链路 1-4 全部有测试。
10. 全部测试通过，无回归。
11. 相同输入在相同 profile 下生成的 Context Governance 结果必须稳定且可复现（deterministic）。任何 degradation 策略禁止引入非确定性因素（LLM 调用、随机采样、时间依赖逻辑）。
